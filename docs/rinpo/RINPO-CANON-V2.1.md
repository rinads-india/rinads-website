# RINPO Canon v2.1

**Status:** canonical consolidation candidate  
**Scope:** product, runtime, character, story and claim governance

## 1. Canonical definition

RINPO is **the humanized interface to the RINADS Intelligence + Execution Runtime**.

RINPO is not merely a chatbot, an LLM wrapper, a prompt library, an n8n workflow, or a customer-support assistant. The authoritative business state remains in RINADS domain services/Supabase; RINPO reasons over that state and may act only through authorized, typed tools.

```text
ANDRINO T D
  -> founder experience + systems thinking
RINADS
  -> business system of record
RINADS INTELLIGENCE
  -> context/reasoning/domain intelligence
RINPO RUNTIME
  -> policy-controlled execution
RINPO
  -> humanized visual/voice/conversational interface
RINPO PHONE / RINADS WORLD / vertical OS surfaces
```

## 2. Document authority

When documentation conflicts, use this order:

1. founder-approved governance/release decision
2. runtime architecture and security gate
3. typed tool and internal-route contracts
4. Facial DNA Lock Sheet v2.0 and Master Turnaround Sheet v2.0
5. production/animation bible
6. brand story/lore
7. legacy prototypes

Security cannot be overridden by marketing or production requirements.

## 3. Runtime laws

Canonical runtime loop:

```text
OBSERVE
 -> CONTEXT
 -> MEMORY
 -> POLICY
 -> INTENT
 -> PLAN
 -> RISK
 -> APPROVAL
 -> EXECUTE
 -> VERIFY
 -> AUDIT
 -> LEARN
```

Non-negotiable properties:

- tenant isolated
- permission aware
- provider independent
- LLM optional
- auditable
- idempotent
- recoverable
- observable
- human controllable
- cost aware
- memory aware
- industry aware
- safe for guarded autonomy

Model output is computation, not authorization.

## 4. Security release law

Production RINPO must enforce:

1. authenticated tenant boundary
2. trusted server-side identity/membership
3. policy authorization for every executable action
4. registered typed tool boundary
5. approval above configured autonomy threshold
6. validated execution context + idempotency
7. postcondition verification
8. auditable intent/policy/approval/execution/verification
9. tenant/user memory isolation
10. model-output non-authority
11. prompt-injection isolation
12. replay protection for mutations

**Release must fail if the RINPO security suite fails.**

## 5. System-of-record boundary

RINPO must never become the authoritative database.

```text
RINADS domain services / Supabase
        -> authoritative state
RINPO Runtime
        -> reason
        -> plan
        -> request approval
        -> invoke authorized tool
        -> verify resulting state
        -> record audit/events
```

## 6. Character canon

Canonical character identity is controlled by the approved v2.0 DNA/turnaround references.

- Name: **RINPO**
- Type: Humanized Digital Intelligence
- Canonical height: **137 cm (4'6")**
- Head proportion: approximately **26%** of total height
- Bald signature silhouette
- Large warm dark-brown/brown eyes
- Thick/soft rounded eyebrows
- Warm South Indian skin tone with stylized realistic texture
- Natural stylized anatomical ears; no anatomical LED/glow
- Default outfit: black RINADS hoodie, black cargo joggers, black/purple RINADS sneakers
- Official RINADS `R` only
- Style name: **RINADS Stylized Cinematic 3D**

If a production document uses a different body height, the v2.0 turnaround reference wins. A miniature/toy-scale render may exist only as a scene-specific variant, not identity scale.

## 7. Character behavior

RINPO should read as intelligent, calm, curious, observant and helpful. Avoid smugness, anger, mocking, meme behavior or exaggerated reactions.

Preferred expression range:

- neutral
- happy
- thinking
- curious
- focused
- brief surprise
- controlled determination

Motion should use child-proportioned gait, short stride and natural micro-expression. No floating/gliding.

Rename any `Founder Mode` costume to **Business / Executive Mode**. Andrino is the founder; RINPO is the intelligence interface.

## 8. Andrino, Moonknight and RINPO

RINPO is not a literal digital replacement of Andrino.

```text
ANDRINO — Curiosity
  -> MOONKNIGHT — Creativity
  -> RINADS — Systems
  -> RINPO — Intelligence
  -> RINADS WORLD — Experience
```

**Moonknight** is preserved as **The Creative Origin of RINADS**: founder archive, photography/visual-storytelling heritage and story chapter. RINADS Studios is the current/future production engine.

## 9. Lore vs history

The banyan-tree awakening and “RINPO became AI” narrative may remain as **RINADS Universe mythic lore**.

It must not be presented as:

- founder biography
- deployed technical architecture
- proof of AI capability

Historical founder material should remain evidence-led and clearly separated from world-building.

## 10. Model/provider architecture

The customer-facing product must not hard-code one model vendor. Model access belongs behind a provider abstraction/ModelGateway.

Core deterministic workflows must degrade gracefully if an LLM provider is unavailable.

## 11. Claim governance

Every public product statement must be classified as one of:

1. **Proven now** — deployed and tested
2. **Designed architecture** — specified/implemented, deployment may vary
3. **Roadmap** — future plan
4. **Lore** — narrative/world-building

Do not make blanket claims such as these unless the specific deployment proves them:

- zero third-party AI
- no external LLM
- data never leaves RINADS
- 100% autonomous
- creates software instantly
- self-evolving production deployment without human approval

Preferred current language:

- provider-independent RINADS intelligence architecture
- models governed through the RINADS intelligence layer
- tenant-isolated, permission-controlled business context
- core operations designed to degrade gracefully if an AI provider is unavailable

## 12. Legacy architecture

The April 2026 n8n/RetellAI/Google Sheets/OpenAI/Twilio/Slack/Gmail voice-agent design remains useful as a prototype and requirements source, but is not the canonical runtime.

A browser-level direct model bridge is also legacy. Browser UI should call server-side RINPO APIs; the server derives identity/tenant context and owns policy, model routing, planning and execution.

## 13. RINPO Phone

RINPO Phone is the common user shell across web/PWA/vertical OS/RINADS World.

The same user should retain the same:

- RINADS identity
- tenant/workspace membership
- permissions
- scoped memory
- business state
- action history

## 14. Thrissur Origin

RINADS World should begin with a focused `Thrissur Origin` experience rather than an immediate Kerala/India-scale world.

Suggested progression:

1. Andrino Origin Room
2. Family Technology Archive
3. Moonknight Studio
4. MA Living Studio
5. Thekkanath Hub
6. Thrissur commerce layer
7. RINADS Office
8. RINADS HQ

Literal current Thrissur locations require dated ground-truth reference plates when geo-accuracy is claimed.

## 15. Final rule

**RINPO may recommend broadly, but may act only through explicit authority.**

**Business Simplified** means fewer interfaces, fewer manual handoffs, controlled automation, verified execution and one consistent intelligence layer.
