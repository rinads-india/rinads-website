# 30 / 60 / 90 Day Engineering Roadmap

**Date:** 2026-08-13  
**Assumption:** Founder approves audit ADRs before BUILD begins. Calendar is indicative sequencing of engineering phases, not a promise of wall-clock dates.

---

## Days 0–30 — Foundation

### Objective

Establish platform boundaries, neutralize security falsehoods, prepare monorepo + brand packages, keep Public Experience online.

### Dependencies

- Founder approval of ADR-001, 002, 006, 010, 011, 012 (minimum)
- No production customer auth requirement yet

### Implementation

- Formalize accepted ADRs under `docs/decisions/`
- Monorepo skeleton; move site to `apps/website`
- Extract `packages/brand` + start `packages/ui`
- Quarantine/remove plaintext localStorage auth (demo badge or disable)
- Rate-limit `/api/chat`; add basic request validation
- CI: lint + typecheck on PR
- SEO baselines: `robots.ts`, `sitemap.ts`, Open Graph
- Curate RINPO assets into versioned folder structure (copy, don’t destroy)

### Database

- Design finalized (already in docs)
- Optional: local Supabase init **without** prod data
- **No** production Supabase customer onboarding

### Security

- P0 auth remediation
- Remove public self-signup to founder/super-admin
- Env example files; secret scanning in CI

### Testing

- Add test runner; smoke tests for chat API validation
- Auth regression tests once Supabase wired in staging

### Deployment

- Staging Vercel target for website
- Stop relying solely on unguarded prod CLI

### Acceptance criteria

- [ ] Website still deploys and renders marketing pages
- [ ] No plaintext passwords persisted
- [ ] Monorepo builds website
- [ ] CI green on PRs
- [ ] ADRs accepted recorded

### Risks

- Monorepo move breaks paths/deploy — mitigate with staged PR + Vercel root directory config
- Over-scoping into CRM — reject (§50)

---

## Days 31–60 — Core platform

### Objective

Stand up RINADS CORE identity + tenancy + RBAC/RLS foundations consumed by website auth.

### Dependencies

- Foundation complete
- ADR-003, 004, 005, 007 accepted
- Staging Supabase project

### Implementation

- `profiles`, `organizations`, `organization_members`, `roles`, `permissions`
- Supabase Auth integration package
- RLS policies + helper functions
- Feature flags table + client helper
- Audit log table + write helper
- Website login uses real auth (flagged)
- Shared UI: Button, Input, Dialog, Toast, Empty/Loading/Error states

### Database

- First real migrations in `supabase/migrations`
- RLS enabled on all tenant tables
- Seed system roles (founder bootstrap controlled)

### Security

- RLS tests
- Service role only on server
- Invite-only elevated roles

### Testing

- RLS isolation tests (org A cannot read org B)
- Auth integration tests
- Permission unit tests

### Deployment

- Staging full stack (Vercel + Supabase staging)
- Migration apply runbook in `docs/deployment/`

### Acceptance criteria

- [ ] User can authenticate via Supabase in staging
- [ ] User belongs to an organization
- [ ] RLS denies cross-tenant reads in tests
- [ ] Audit log records privileged actions
- [ ] Website marketing unaffected for logged-out users

### Risks

- Incorrect RLS (fail open) — require tests before merge
- Billing built too early — defer

---

## Days 61–90 — Intelligence + RINPO

### Objective

Introduce Intelligence app skeleton and upgrade RINPO from marketing companion to permissioned assistant (read/recommend first).

### Dependencies

- CORE auth/orgs/RBAC/audit live in staging
- ADR-008, 009 accepted

### Implementation

- `apps/intelligence` shell (Founder dashboard IA, empty modules)
- `packages/ai` orchestration stub + tool registry
- RINPO tools: `get_pending_tasks` style **read** tools only (even if backed by thin tables)
- Approval workflow tables for future writes
- Wire RINPO states + personality config; keep character bible
- Optional: replace keyword chat with model-backed **recommend-only** answers behind flag
- n8n only for notification experiments — not core logic

### Database

- `ai_tool_*`, `ai_approvals`, `rinpo_preferences`
- Minimal ops tables only if needed for demos (tasks)
- Still no full ERP/CRM

### Security

- AI cannot bypass RLS
- No destructive tools enabled
- Invocation auditing

### Testing

- Tool permission denials
- Approval required for write tools (even if writes disabled)
- RINPO UI regression on website

### Deployment

- Intelligence app on staging
- Feature flags: `rinpo_enabled`, `ai_insights_enabled`

### Acceptance criteria

- [ ] Intelligence app deploys separately from website
- [ ] RINPO can READ one scoped dataset and RECOMMEND
- [ ] EXECUTE destructive actions impossible without approval path
- [ ] Character assets unchanged unless Founder-approved

### Risks

- Premature autonomy
- Model cost without caching/routing policy
- Scope creep into RINAGLOW — defer to post-90

- Full CRM/ERP modules

- Autonomous AI execute
